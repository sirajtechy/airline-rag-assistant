Section 1

The assignment, and what it actually rewards

The grading weights in data/raw/EVALUATION_METHODOLOGY.md put the majority of the marks on measured evidence rather than on a working chat interface. The study is the deliverable.

Grading weights (REQUIREMENT.md section 9)
WeightComponentWhat is required
40% Evaluation rigour 8 ablation tables, real measured numbers, written winner justification per stage
30% Routing Correct passenger-vs-cargo routing on the 5 acceptance tests
20% End-to-end judged quality RAGAS + DeepEval scores on the final pipeline
10% Code quality / app Working chatbot, usable interface, maintainable code
Key framing

This is not “build a chatbot”. It is “run a rigorous 8-stage ablation study and ship the winning config”. The methodology states plainly that a chatbot which just works, with no evaluation evidence behind it, caps at the 30% line and cannot pass on functionality alone. Every configuration choice in this project therefore has a table behind it, including the choices that were rejected.

Note also what the 20% row does not say. It asks for scores, not for scores above some line: neither spec file contains a threshold, pass mark or minimum anywhere. See what the spec does and does not require.

The corpus

One airline, three real business lines — 45 PDF pages and 2 XML files. The three-way split is what makes the routing requirement non-trivial: the vocabulary overlaps heavily across documents while the correct answers do not.

Architecture

All retrieval, routing, guardrail and generation logic lives in the transport-agnostic delta_rag package. The FastAPI backend and the four notebooks both call the same code, so the application and the evaluation cannot drift apart.

Section 3

The foundation: ground truth before design decisions

The chunk-ID trap

Stage 1 varies the PDF parser. Stage 2 varies the chunking strategy. Both change chunk boundaries and therefore chunk IDs. Ground truth recorded as “chunk #47 is correct” is destroyed by the first two experiments — and every table after them would be measuring noise while still looking authoritative. The labelling scheme has to be invariant to both.

Label schema — parser- and chunker-invariant
FieldMeaningExample
gold_docStable document identifiercontract_of_carriage
gold_locatorsPDF page or XBRL conceptp17  /  us-gaap:NetIncomeLoss
gold_spanVerbatim answer-bearing text, whitespace-normalised“Delta reserves the right to sell more tickets…”
Graded relevance, derived mechanically at scoring time
GradeConditionInterpretation
3Chunk contains the verbatim gold spanAnswer-bearing
2Right document, at a gold locator, span not intactRight page, mangled text
1Right document, elsewhereRight document, wrong place
0Different documentWrong document
Design decision

The binary relevance threshold is grade ≥ 2, not 3. pypdf extracts “those” as “t hose” on contract page 4, so one gold span is unrecoverable from its output. Requiring grade 3 would score that mangled-but-correct page as a total retrieval miss — overstating the damage and double-counting a parser that is already penalised in the Stage 1 gold-span-recoverability column. At grade ≥ 2 the defect costs NDCG@3 (graded) and leaves R@3 (binary) intact: counted once, in one place. A unit test (test_relevance_threshold_is_grade_two) pins the threshold so it cannot drift.

The evaluation set

Questions30
By route12 passenger / 11 cargo / 7 financial
By query type14 keyword / 16 semantic
Gold spans verified30 / 30 machine-checked

Built before any pipeline decision. The keyword/semantic split exists because Stage 5 requires it, so it had to be authored up front rather than reconstructed afterwards. Labels are gated against one reference parser (pymupdf) so ground truth stays fixed while Stage 1 varies the parser under test; per-parser span recoverability is then reported as Stage 1 evidence rather than treated as a label failure.

The validator caught two real problems rather than merely passing:

  • A labelling error of my own. Diluted EPS renders as “USD 7.66” because the XBRL unit is usdPerShare, not the dollar-formatted string I had written.
  • A genuine pypdf extraction defect — the “t hose” split on contract page 4, which then became the evidence behind the grade-≥-2 decision above.

Metrics

R@1, R@3, MRR@10, DCG@3 and NDCG@3 are implemented directly from the specification definitions rather than pulled from a library, and pinned by 30 unit tests against hand-worked values. For example, DCG@3 over grades [3, 2, 1] is 3/log₂(2) + 2/log₂(3) + 1/log₂(4) = 4.76186. A library disagreeing with that number would be a library using a different DCG convention, which is precisely the kind of silent drift the tests exist to catch.

Hypothesis refuted

The financial route scored R@3 = 0.1429 on sparse retrieval. Dense and sparse retrieval fail in different ways, so their failing identically pointed at the corpus, not the config. The obvious culprit was boilerplate: 420 records sharing an entity/filing header and repeating “for the period 2025-01-01 to 2025-12-31” on nearly every line, leaving roughly 80% shared vocabulary. Variant B removes exactly that.

Removing all of it changed nothing. Sparse financial R@3 stayed at 0.1429 and dense stayed at 0.5714. Only dense MRR@10 moved (0.5083 → 0.6071), i.e. slightly better ordering of results that were already being found. The hypothesis was wrong, and the table records it as wrong.

The real defect was a vocabulary gap. US-GAAP names the element “Revenue from Contract with Customer, Excluding Assessed Tax”; a human asks for “total operating revenue”. Those strings share almost no terms — fatal for BM25, merely bad for embeddings. Bridging it took sparse from 0.1429 to 0.7143 (5×) and dense from 0.5714 to 0.8571.

Caveat stated plainly: the alias map is the single largest lever on this route and synonym injection is inherently at risk of being fitted to the evaluation questions. The aliases were authored from standard 10-K statement line-item conventions rather than from the eval set, and are reported here in isolation (variant B vs C) precisely so a sceptical reader can discount them.

The mechanism matters more than the delta. A table of contents is worse than useless. It lists every rule title in the document — RULE 20: DENIED BOARDING COMPENSATION, G32 Limit of Liability — so to BM25 it looks maximally relevant to almost any topical query while containing no rule text to answer with. It is a chunk engineered to win retrieval and then say nothing.

The running header is the subtler defect. Delta Domestic General Rules Tariff appears on all 23 pages of the passenger contract, so the terms “domestic”, “rules” and “tariff” are indexed 23 times inside the passenger document. That is why a cargo question phrased as “rules for shipping cargo domestically” was pulled toward the passenger contract. The cross-contamination this group is specifically graded on was partly caused by page furniture.

This was found by debugging a failing required acceptance test, not by reading the PDFs. The aggregate retrieval metrics were already respectable while that test was failing for a cause no aggregate number surfaced.

Statistical margin

With n = 30, one question is worth 0.0333 of R@3. The top four configurations here all tie at R@3 = 0.9000 and are separated by less than 0.01 MRR@10 — under a third of one question. recursive 500/50 is selected on the declared metric priority, but the honest reading is that chunking strategy is not a decisive lever on this corpus once front matter is removed. This winner should be read as “no worse than the alternatives”, not “better”.

Negative result

rule_aware was a custom, document-specific strategy I built to split on the documents' own RULE 20: / G14 headings, on the reasoning that a rule heading is a genuine semantic boundary rather than an arbitrary token offset. I expected it to win. It did not. Both tariffs are already written as short numbered rules, so any sane splitter lands boundaries in roughly the right place anyway. That is a useful negative result about how much document-specific engineering this corpus actually rewards — and the only way to know was to build it and measure it against the generic strategies.

This stage is a tie, and it used not to be

An earlier synthesis of this project recorded bge-small beating MiniLM by +0.1333 R@3 — four questions on a 30-question set, which would have made the embedding model one of the larger levers in the study. That measurement was taken before the Stage 0b corpus cleaning removed two pages of front matter and running headers. Re-run against the cleaned corpus, the gap is 0.0000: both models land R@3 0.9000, which is 27 of 30 questions each, and they split the ranking-quality metrics between them.

The lesson is about the order of operations, not about embeddings. Cleaning the corpus removed the leverage of the embedding model: once the boilerplate was no longer competing for similarity, the weaker model stopped losing questions to it, and the difference the stage was measuring disappeared. A stage measured against a defective corpus can report a real, reproducible difference that does not survive fixing the defect. Data defects should be hunted before component sweeps, or the sweeps end up measuring the defect.

bge-small still ships — it is no worse on any metric that decided a downstream stage, and Stages 4–7 were all measured on it — but the honest reading of Stage 3 is “these two are interchangeable on this corpus”, not “bge-small is better”.

bge-small and nomic are asymmetric models: they are trained to embed queries and passages with different instruction prefixes. Those prefixes are applied here (Represent this sentence for searching relevant passages: and search_query:/search_document: respectively). Benchmarking them without their prefixes is a common error that would have understated both and handed the stage to MiniLM by default. Latency is measured after a warm-up call so model load is excluded; nomic pays a network round-trip to Ollama that the two in-process sentence-transformers models do not.

Winner FAISS — selected on operational grounds, not quality. Retrieval metrics are identical to four decimal places.

R@3 is reported as a parity check and behaves as the methodology predicts: identical embeddings retrieve near-identically regardless of store, so this decision cannot be made on quality. FAISS builds its flat inner-product index roughly 4,000× faster at this corpus size and runs in-process with no server, but has no native metadata filtering — business-line scoping has to be emulated by over-fetching and post-filtering. ChromaDB supports where filtering natively. At ~500 chunks the over-fetch cost is negligible and the build-time advantage is what makes the whole ablation matrix practical to re-run. ChromaDB would be the better choice if this corpus grew by an order of magnitude, where post-filtering starts to threaten recall.

Why hybrid is justified

The two retrievers have opposite weaknesses, not one dominant mode. Sparse is perfect on passenger (1.0000) and collapses on financial (0.7143) — passenger questions quote tariff vocabulary almost verbatim, which is BM25's home ground. Dense is the reverse: strong on financial (0.8571), weakest on cargo (0.5455).

Hybrid does not split the difference. On semantic queries it beats both — 0.9375 against 0.7500 dense and 0.8750 sparse. That is the argument for paying the complexity cost of running two retrievers and fusing them. Had one mode dominated every column, fusion would have been unjustifiable complexity and this table would have said so.

Statistical margin

Weighted alpha = 0.5 leads RRF on R@3 by 0.0333, which on 30 questions is exactly one question — the resolution limit of this eval set. The win is real but weakly evidenced.

Worse, the alpha sweep is non-monotonic: R@3 runs 0.8667 → 0.8667 → 0.9333 → 0.8667 → 0.8000 across alpha = 0.2 → 0.8. If alpha were capturing a real property of the corpus the curve would be smooth. A spike at a single point is what overfitting to a small set looks like, not a tuned optimum.

RRF remains the safer production choice — it carries no hyperparameter to overfit and is invariant to the two retrievers' score scales, at the cost of being blind to margin. If this eval set grew to 100+ questions I would expect the gap to close. The measured winner is reported as measured, with the caveat attached.

Negative result

The reranker is rejected — it makes retrieval worse, not better. NDCG@3 falls from 0.8849 with no reranker to 0.8388 at top-10 and 0.8343 at top-20. R@3 drops from 0.9333 to 0.8667 at both pool sizes. It costs 176.2 ms at top-20 to be worse, and the damage grows with the candidate pool: the more documents it is given to reorder, the more harm it does. This is the opposite of the textbook result, so it needs an explanation rather than a shrug.

(a) Domain mismatch. ms-marco-MiniLM-L-6-v2 is trained on MS MARCO — short, factual web-search passages answering natural questions. This corpus is neither: it is dense legal tariff prose full of cross-references (as provided in Rule 20(c)(1)) and XBRL records that read as label-plus-numbers. The cross-encoder's learned notion of relevance transfers poorly to both, so its confident reordering is confidently wrong.

(b) No headroom. Hybrid fusion already reaches R@3 = 0.9333. A reranker cannot add documents fusion never retrieved — it can only reshuffle what is already there. When the correct chunk is usually already in the top 3, any reshuffling is far more likely to demote it than to promote it.

The general lesson is the one the methodology is built around: a reranker is a conditional improvement, not an automatic one. Adding it on tutorial precedent would have cost this pipeline both accuracy and latency.

Status — what is measured, and what is deliberately still empty

RAGAS is complete for both judged models, and so are three of DeepEval's four metrics. Faithfulness, answer_relevancy and the custom G-Eval PolicyAccuracy criterion are read straight out of reports/results/stage8_scores__deepeval.json for both qwen2.5:7b and llama3.2:3b.

The cached values were produced by the misconfiguration documented in war story a — HallucinationMetric: the metric was handed the five retrieved chunks where it expects ground truth, so it measured retrieval breadth rather than hallucination. Those figures are not results and are not presented as results — the superseded value is quoted once, inside that war story, explicitly labelled invalid. Re-scoring is under way. No placeholder, averaged or estimated value stands in for a measurement anywhere in this table.

To complete it: scripts/rescore_hallucination.py recomputes that one metric against the labelled ideal answers and keeps the other three from cache. A corrected entry is identifiable by its hallucination_context key, which records that ground truth rather than retrieval output was used; an entry without that key must not be read as a hallucination result.

Cost cannot decide this stage

Cost per query is $0.00 for every row, because every candidate runs locally on Ollama. The spec asks for a cost column and it is reported honestly, but a column that is constant down the table carries no information: it cannot discriminate between candidates at all. Latency and judged quality therefore do all of the work in this decision.

That is exactly what makes llama3.2:3b tempting and what makes it rejectable anyway. It answers in 8.42 s against 16.41 s, and both are free — but it gives up 0.1157 of RAGAS faithfulness (0.7829 vs 0.8986), 0.0844 of answer relevancy (0.6560 vs 0.7404) and 0.2000 of valid-citation rate (0.7333 vs 0.9333) to get there. On a policy bot, a cited figure that the retriever never returned is the most expensive kind of error, and it is not made cheaper by arriving twice as fast.

Control check — the experiment was correctly controlled

context_precision (0.7676) and context_recall (0.9139) are identical across the two models — to seven decimal places in the raw artefact. This is exactly as expected: retrieval was held fixed while only the generator varied, and those two metrics are properties of the retrieval, not of the generator. Had they differed, something other than the generator would have changed between runs and the comparison would be void.

The two metrics that do depend on the generator move as expected: qwen2.5:7b leads llama3.2:3b on faithfulness (0.8986 vs 0.7829) and on answer_relevancy (0.7404 vs 0.6560) — consistent with its higher valid-citation rate in the quota-free table above.

The second judge independently reproduces that ordering. DeepEval also puts qwen2.5:7b ahead of llama3.2:3b on faithfulness (0.6644 vs 0.6359), on answer_relevancy (0.7096 vs 0.6991) and on G-Eval PolicyAccuracy (0.9867 vs 0.9000). The two judge families disagree on the level of faithfulness — sharply, see below — but they agree on the ranking, which is the thing this stage actually has to decide. A choice of generator that survives both judges is better evidenced than either judge's absolute number.

The two frameworks run under deliberately different judge model families: qwen2.5-7b-judge for RAGAS, llama3.1-latest-judge for DeepEval. That choice was made before any score existed, so that agreement between the frameworks would carry information rather than restate one model's opinion twice. Both frameworks compute faithfulness and answer relevancy, and qwen2.5:7b's answers have now been scored by both, so the two figures can be put side by side.

Finding — close on relevancy, sharply split on faithfulness

The two judges land 0.031 apart on answer relevancy and 0.234 apart on faithfulness. Answer relevancy is close enough to treat as corroborated by two independent readings. Faithfulness is not: a 0.234 spread is larger than almost every margin this study used to pick a winner elsewhere — larger than the entire Stage 6 fusion decision (0.0333) by a factor of seven.

The honest conclusion is that neither faithfulness figure should be treated as precise. The defensible statement is “this pipeline sits somewhere in the 0.66–0.90 band on faithfulness, and the measurement is not sharp enough to say where”. It is emphatically not “0.8986”, and picking that number because it is the flattering one would be exactly the failure the rule above was written to prevent.

What the two judges do agree on is the ranking: both put qwen2.5:7b ahead of llama3.2:3b on both shared metrics. That is the claim Stage 8 needs, and it is the claim that is properly evidenced. The absolute faithfulness level is not.

This is direct empirical vindication of using two different judge families. Running RAGAS and DeepEval on the same judge model would have produced agreement close to by construction, and that false agreement would have been reported as a confident faithfulness number with two frameworks' worth of apparent support behind it. The disagreement is the finding; a single judge would have hidden it. See war story h — judge independence, and the limitation stated in section 8.

What the spec does and does not require

Grepping data/raw/EVALUATION_METHODOLOGY.md and data/raw/REQUIREMENT.md for any threshold, pass mark or minimum score returns nothing. That is worth stating plainly, because a DeepEval faithfulness figure of 0.6644 invites the question “is that a pass?” — and the question is not well formed.

  • There is no required minimum for faithfulness or for any other metric. The 20% is awarded for “End-to-end RAGAS + DeepEval scores on the final chosen pipeline” — that is, for reporting real measured numbers on the pipeline that actually shipped, not for clearing a bar. A target would only create an incentive to tune against the judge, which would destroy the one thing these numbers are for.
  • The threshold=0.7 passed to the DeepEval metrics is not a pass mark either. It only sets an internal metric.success boolean. Every figure reported here is metric.score, so no threshold anywhere in this codebase influences a single number in this report.
  • Local models are a compliant choice, not a shortcut. Stage 8 of the methodology asks to “Compare at least 2 real LLMs (e.g. Gemini 2.5/2.0 Flash, GPT-4o-mini, Claude Haiku, a local Ollama model)” — an “e.g.” list that names local Ollama models outright. Two judged models meets the stated minimum; four were generated and measured on the quota-free metrics above.
  • This report is a superset of the required columns. The spec's Stage 8 table asks for Faithfulness, Answer Relevancy and Context Precision from RAGAS, Hallucination and G-Eval from DeepEval, plus cost and latency. Table 8b reports all of those and adds DeepEval faithfulness, DeepEval answer relevancy and RAGAS context recall — the first two precisely so that the cross-judge comparison above is possible at all, the third as the control that proves retrieval was held fixed.

Known limitation: R2

R2 — “What is Delta's liability limit for a damaged shipment?” — routes to the passenger contract, whose baggage-liability clause is genuinely the most topically similar text in the corpus and even quotes a dollar figure ($4,700 per passenger). A retriever is not wrong to surface it. The distinguishing signal is not similarity but vocabulary: “shipment” is a term the cargo tariff defines and the passenger contract does not.

The defined-term prior fixes R2 — and breaks R1. Shipping a fix validated on the single case it was built for would be overfitting, so no fix was shipped. It is documented as a limitation instead.

Guardrails: three deterministic checks plus a confidence floor

Pre-retrieval

Out-of-scope carrier

Deterministic detection of another airline in the question. Returns a canned refusal naming Delta's three source documents. Runs before the carrier's name can contaminate retrieval, and before the live-data check so “status of my JetBlue flight” is refused as out of scope rather than merely deflected.

Pre-retrieval

Live-data request

Detects booking, flight-status and account intent. Explains the bot answers general policy questions from published documents only, and offers what it can answer. No LLM call is made.

Post-retrieval

Abstain gate

Dense cosine similarity floor at 0.67 on the single best-matching chunk. Cosine is used rather than the fused score because RRF scores are a rank artefact with no absolute meaning and no cross-query comparability; cosine is bounded in [0, 1].

Post-generation

Citation verification

Every [n] marker in the answer is checked against the retrieved source list. The API returns citations_valid and the UI surfaces it, so an unverified answer is visible rather than silent.

Abstain threshold calibration

Measured over the 30 answerable evaluation questions against 8 deliberately unanswerable probes (international fees, SkyMiles earning, lounge hours, aircraft configuration — plausible Delta questions whose answers are genuinely outside these three documents, and deliberately avoiding competitor names and “my booking” phrasing so they exercise this gate rather than the deterministic guards).

Two-layer defence

The abstain gate is the coarse outer layer, deliberately tuned to reject no answerable question. The precise layer is the system prompt, which makes the model decline from context it can actually read.

Acceptance probe G4 proves it. Asked for a transatlantic third-bag fee, the bot answered:

“Delta's published documents do not cover checked bag fees for transatlantic flights as these are U.S. domestic rules only [1]. Therefore, I cannot provide the specific fee amount you're asking about based on the given sources.”

That is a grounded refusal with a citation, on a question whose retrieval confidence was high. Cosine similarity could never catch it, because the retrieved baggage rules genuinely are the most topically similar text in the corpus — they simply do not contain the answer. Tightening the cosine gate would buy refusals the prompt layer already handles better, while losing real answers.

Section 7

Engineering war stories

Eight problems that cost real time and that no tutorial warns about. Each is the kind of failure that silently corrupts an evaluation rather than crashing it. The first one is the most important thing in this document: a metric that ran cleanly for 45 minutes per model and reported a number about the wrong quantity.

a — Measurement validity

DeepEval's HallucinationMetric was measuring retrieval breadth, not hallucination

ProblemDeepEval's HallucinationMetric returned 0.5868 for qwen2.5:7b. Lower is better on that metric, so 0.5868 implies heavy hallucination — the answers contradicting their sources more often than not. Yet DeepEval's own FaithfulnessMetric, run by the same judge over the same answers, returned 0.6644. Those two readings are close to self-contradictory: the same framework was simultaneously reporting that two thirds of the content was grounded and that more than half of it was unsupported. The obvious first interpretation was the wrong one — that a small local judge simply cannot be trusted.
DiagnosisReading DeepEval's source settled it in minutes. HallucinationMetric._calculate_score reduces to:
number_of_verdicts  = len(self.verdicts)
hallucination_count = # number of verdicts whose verdict == "no"
score               = hallucination_count / number_of_verdicts

It emits one verdict per document in context, and scores the fraction of those documents the answer does not align with. The pipeline was handing it all five retrieved chunks as context. A correct, well-grounded answer normally draws on only one or two of those five — so the remaining three or four correctly produce “no” verdicts, and each one pushes the score up. The metric was measuring retrieval breadth, not hallucination. Retrieve top-10 instead of top-5 and the same answers would have looked twice as hallucinatory.

Crucially, DeepEval intends context to be ground-truth context. Retrieval output belongs to FaithfulnessMetric via retrieval_context — which the pipeline was already doing correctly. So faithfulness was sound the whole time; only the hallucination metric was being fed the wrong thing.

Fixcontext now receives the curated ideal answer from the labelled evaluation set — genuine ground truth — so hallucination now measures what its name claims: whether the answer contradicts the known-correct answer. scripts/rescore_hallucination.py recomputes only that one metric and preserves faithfulness, answer relevancy and G-Eval from the completed cache, saving roughly 45 minutes per model over a full re-run. The 0.5868 reading is retired; it appears in this document only in this card, labelled as the invalid first run.
Lesson

An eval metric that runs without raising is not the same as an eval metric that measures what you think it measures. Nothing failed here. No exception, no NaN, no warning — just a plausible number, computed correctly, attached to the wrong quantity.

And the wrong reading was not random noise. It was a systematic bias in a specific, explainable direction: more retrieved chunks means a worse apparent hallucination score. That makes it far more dangerous than noise. Noise looks like noise and averages away; a systematic bias survives averaging, survives repetition, survives a bigger evaluation set — and looks like a finding.

It very nearly produced a false conclusion in this report. “Local judges are self-contradictory and unreliable” was measurement error on my side, not a property of the judges, and it would have been written up as a result. The genuine judge-related caveat is much narrower: the 0.234 faithfulness disagreement between two different judge families.

b — Performance

Ollama allocates the maximum context window by default

ProblemGeneration took 30 seconds per answer, and per-model evaluation runs took between 52 minutes and 6.9 hours.
DiagnosisOllama allocates each model's maximum context unless told otherwise — 131,072 tokens for Llama 3.1 — reserving roughly 22 GB of GPU memory for a prompt that never approached it.
FixCap num_ctx at 8192. GPU reservation dropped to 5.9 GB and per-model eval runs dropped to 3–7 minutes.
c — Correctness

Silent NaN in evaluation frameworks

ProblemJudge scores that looked plausible but were computed over almost no data.
DiagnosisA rate-limited or timed-out judge call does not raise — it returns NaN. A mean taken over mostly-NaN values still produces a number, and that number looks like a real score.
FixTreat any harness that coerces failures into numbers as reporting confident nonsense until proven otherwise. Count non-NaN samples explicitly and refuse to report a metric that is missing data.
d — Dependency

RAGAS import crash on a package it never uses

ProblemImporting RAGAS raised an ImportError on a clean environment.
DiagnosisRAGAS imports langchain_community.chat_models.vertexai, which current langchain-community no longer ships — even though this project never touches Vertex AI.
FixRegister a stub module under that name before the RAGAS import. The course's own requirements.txt notes the same problem, so this is not local breakage.
e — Dependency

DeepEval's hard-coded OpenAI model whitelist

ProblemPointing DeepEval at a local OpenAI-compatible endpoint was rejected despite the endpoint working for everything else.
DiagnosisGPTModel validates the model name against a hard-coded OpenAI whitelist, so an OpenAI-compatible base URL is not sufficient — the name has to be an OpenAI name.
FixSwitch to DeepEval's native OllamaModel / GeminiModel classes rather than fighting the whitelist.
f — Measured and rejected

Gemini free tier cannot sustain a judged evaluation

ProblemHosted judging looked like a way to get a stronger judge than a local 7B model.
DiagnosisRAGAS needs roughly 330 LLM calls per candidate model — context precision alone costs one call per retrieved context. The Gemini free tier allows about 20 requests per minute per model. Client-side pacing at 12 RPM still drew 429s, each carrying a server-mandated backoff of about 48 seconds, stalling throughput to 2 jobs in 9 minutes. Separately, the /v1beta/models listing advertises models new keys cannot call: gemini-2.5-flash returns 404 “no longer available to new users”.
FixLocal judges. They have no quota — the actual binding constraint — and returned complete scores with no NaN. Gemini is now opt-in behind DELTA_RAG_JUDGE=gemini for anyone with a paid key.
g — Self-inflicted

Resource contention from orphaned processes

ProblemIdentical API calls degraded run over run: 43 s → 57 s → 76 s → 78 s. Nothing in the code had changed.
DiagnosisOrphaned Python processes left behind by interrupted evaluation runs had driven the 15-minute load average to 21. The benchmark was measuring the machine, not the pipeline.
FixKill the orphans before timing anything. Warm generation returned to roughly 2 seconds. Any latency number taken during that window is worthless.
h — Methodology

Judge independence is not automatic

ProblemRunning RAGAS and DeepEval both feels like two independent checks on the same pipeline.
DiagnosisRunning both frameworks on the same judge model measures one model's opinion twice and then calls the agreement corroboration. It is a single point of failure wearing two hats.
FixDeliberately different model families: qwen2.5:7b for RAGAS and llama3.1:8b for DeepEval. Where the two frameworks then disagree, the correct conclusion is that neither number is reliable.
It paid offThis was a precaution taken on principle, and it returned a measured result: the two judges came out 0.031 apart on answer relevancy but 0.234 apart on faithfulness for the same answers. One judge family would have reported a single confident faithfulness number, and two frameworks on that one judge would have made it look corroborated. See judge agreement.

What actually moved the needle, ranked by measured impact

  1. Vocabulary bridging on the financial route. Sparse financial R@3 went 0.1429 → 0.7143 (5×) and dense 0.5714 → 0.8571. Nothing in Stages 1–7 came close.
  2. Removing 2 of 45 pages of front matter. Fixed a failing required acceptance test; sparse R@3 0.7667 → 0.8333, cargo R@3 0.6364 → 0.7273, hybrid NDCG@3 0.8594 → 0.8874.
  3. Hybrid retrieval. +0.1666 R@3 over dense, and the only configuration that is strong on all three routes.
  4.   5. Chunking, fusion method, vector store. Differences at or inside the noise floor of a 30-question set — and, on the current artefacts, the embedding model belongs in this group too.

The uncomfortable conclusion

The two largest wins came from looking at what the retriever actually returned, while the canonical hyperparameter sweeps mostly produced ties. Both were found by investigating a failure, not by tuning: the financial defect surfaced because dense and sparse failed identically (a tell that the corpus, not the config, was at fault), and the boilerplate defect surfaced because an acceptance test failed while every aggregate metric looked healthy.

Artefact drift — disclosed

The narrative synthesis in reports/REPORT_TEMPLATE.md was written against an earlier run and records “+0.1333 R@3” for bge-small over MiniLM, and an RRF selection for Stage 6. That R@3 figure predates the Stage 0b corpus cleaning and does not survive it. The current measured artefacts in reports/results/ supersede both: Stage 3 shows MiniLM and bge-small tied at R@3 0.9000, with bge-small ahead on MRR@10 (0.8011 vs 0.7889) and DCG@3 (3.7964 vs 3.7412) and MiniLM ahead on NDCG@3 (0.8844 vs 0.8762); and the shipped final_retrieval_config.json uses weighted linear at alpha = 0.5. Every table in this document is rendered from the JSON artefacts, not from the narrative. Re-running scripts/build_report.py reconciles the prose.

Where the evidence is weak, stated plainly

  • n = 30 is coarse. One question is worth 0.0333 R@3, so Stage 2, Stage 4 and Stage 6 are all decided inside the noise floor. Those winners should be read as “no worse than the alternatives”, not “better”.
  • The alias map is the single largest lever and the most exposed to test-fitting. It was written from 10-K statement conventions rather than from the eval questions, and is measured in isolation (Stage 0 variant B vs C) so it can be discounted — but a held-out financial question set is the only real check.
  • The two judges disagree on faithfulness by 0.234, and both are local 7–8B models. On identical answers and identical contexts, RAGAS (qwen judge) reports 0.8986 and DeepEval (llama judge) reports 0.6644; they agree to within 0.031 on answer relevancy. So the answer-relevancy figure is corroborated and the faithfulness figure is not — neither faithfulness number should be read as precise, and the defensible claim is a 0.66–0.90 band. Local judges are cheap and reproducible, but weaker than a frontier judge, and that is the most likely source of the spread. Full working in judge agreement.
  • An earlier draft of this section called the judges “self-contradictory”. That was wrong, and the correction matters more than the original claim. The specific contradiction — an implausibly bad hallucination score sitting next to a faithfulness score of 0.6644 from the same framework — was my misuse of DeepEval's HallucinationMetric, which had been handed five retrieved chunks where it expects ground truth. It was measuring retrieval breadth. The judges were not contradicting themselves; the harness was asking one of them the wrong question. See war story a. The genuine limitation is the 0.234 faithfulness disagreement above, which is a narrower and better-evidenced claim.
  • R2 is a known misroute. “Liability limit for a damaged shipment” routes to the passenger contract. The defined-term prior fixes it but breaks R1, so no fix was shipped on the strength of one case.

What I would try next

  1. A held-out financial eval set phrased with vocabulary absent from the alias map. This is the biggest threat to the project's headline claim and the cheapest to test.
  2. LLM-based groundedness instead of a cosine floor. Probe G4 showed the model refusing correctly at high retrieval confidence — it can read the context and see the answer is absent, which cosine similarity fundamentally cannot. The threshold gate is the weakest component: the answerable and unanswerable score distributions overlap, so no threshold separates them.
  3. A domain-tuned reranker. The Stage 7 failure was diagnosed as MS MARCO training data not transferring to legal tariff prose. Fine-tuning a cross-encoder on tariff-style pairs would test that diagnosis directly, rather than assuming it.
  4. Multi-hop questions. Every current eval question is answerable from one chunk. A real question like “I was bumped and my bag was damaged — what am I owed?” needs Rule 20 and Rule 17 simultaneously, and flat top-k retrieval has no mechanism for composing two rules.
  5. Cross-route answers. Routing commits to exactly one business line to prevent contamination. A shipper asking a question that legitimately spans the cargo rules and the financial filings cannot be served at all — the anti-contamination fix has a cost this eval set never probes.
